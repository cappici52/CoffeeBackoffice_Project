# การจำลองการขายและทดสอบพยากรณ์ 30 วัน

ข้อมูลทั้งหมดในกระบวนการนี้เป็น **ข้อมูลสังเคราะห์** ไม่มีลูกค้าจริง ไม่มีการโอนเงินจริง และไม่ใช้เป็นหลักฐานความแม่นยำของร้านจริง

ผลรอบที่ทำเสร็จแล้ว: [การทดลองวันที่ 3 พฤศจิกายน 2026](sales-simulation-results-2026-11-03.md)

## รันซ้ำ

ต้องมี PostgreSQL ในเครื่อง บัญชีใน `.env` มีสิทธิ์สร้างฐานข้อมูลใหม่ ติดตั้ง Python dependencies ตาม README และให้พอร์ต loopback 18002 ว่าง

```powershell
npm run test:simulation
npm run simulation:sales
npm run simulation:report
# เปิดเว็บจากฐานจำลองที่รันสำเร็จล่าสุด (หลังจบรอบเท่านั้น):
npm run simulation:preview
# อีก terminal เมื่อ preview เปิดแล้ว:
npm run test:simulation-preview
```

ใช้เวลาในการรันตามความเร็วเครื่องและฐานข้อมูล ไม่จำเป็นต้องปิดแอปร้านจริง ขณะรันควรหลีกเลี่ยงแก้ยอดร้านจริง เพราะมีการเปรียบเทียบ fingerprint ก่อนและหลังเพื่อยืนยันว่าข้อมูลไม่เปลี่ยน หากเปลี่ยนจากกิจกรรมอื่น การตรวจสอบจะหยุดเพื่อให้ตรวจสาเหตุ

สคริปต์สร้างฐานข้อมูลใหม่ชื่อ `coffee_sim_<เวลา UTC>_<ค่าสุ่ม>` ทุกครั้ง ไม่รับชื่อฐานข้อมูลปลายทางจากผู้ใช้ ไม่ใช้ฐานข้อมูลที่มีอยู่ และไม่ลบฐานข้อมูลอัตโนมัติ ข้อมูลและผลลัพธ์อยู่ใน `.local/simulation/` ซึ่งถูก ignore จาก Git; `latest.json` ชี้เฉพาะรอบที่สำเร็จ รอบที่หยุดกลางทางไม่ใช่ผลทดสอบสมบูรณ์

โหมด `NODE_ENV=production` และ PostgreSQL ที่ไม่ได้อยู่บน loopback ถูกปฏิเสธ โปรแกรมอ่านฐานข้อมูลร้านจริงเฉพาะ fingerprint ของ orders/payments/ingredients/stock_movements/forecast_runs/day_closings และใช้การเชื่อมต่อ admin สร้างฐานข้อมูลทดสอบแยก ไม่รัน migration หรือ seed บนร้านจริง

## สถานการณ์ที่ทดสอบ

- สร้าง owner/cashier/kitchen ของรอบจำลอง รหัสผ่านสุ่มใช้เฉพาะในหน่วยความจำ ไม่คัดลอกบัญชีจริง
- 8 เมนูและตัวเลือกเสริม; สูตรทดสอบแบบย่อ 2 วัตถุดิบ เพื่อให้ตรวจบัญชีสต็อกได้ชัดเจน ไม่ใช่สูตรประกอบอาหารจริงของร้าน
- QR ประจำโต๊ะและ POS แบบทานที่ร้าน ส่งออเดอร์ ยืนยันก่อนทำ KDS เริ่มทำ/พร้อมเสิร์ฟ ส่งมอบก่อนรับชำระ เงินสดและบันทึก PromptPay
- ยกเลิกก่อนยืนยัน ยกเลิกหลังยืนยันแต่ยังไม่เริ่มทำ/คืนสต็อก ยกเลิกหลังเริ่มทำ/ไม่คืนสต็อก และคืนเงินโดย owner; cashier ไม่มีสิทธิ์อนุมัติคืนเงิน
- ส่งคำสั่งซื้อซ้ำ ยืนยันซ้ำ รับชำระซ้ำบางรายการ รับเข้าสต็อก ของเสีย สต็อกไม่พอและเติมฉุกเฉิน
- ตรวจสถานะผ่านลิงก์ลูกค้า ปิดวันไม่ได้เมื่อมีบิลเสิร์ฟแล้วยังไม่ชำระ ปิดวันซ้ำไม่ได้
- ตรวจยอดเงินสด + PromptPay = ยอดรับชำระ ตรวจเงินรับตรงบิล ไม่มีบิลค้าง ไม่มีออเดอร์ค้าง และสต็อกคงเหลือตรงผลรวมการเคลื่อนไหว

รายการขาย การรับชำระ การเปลี่ยนสถานะ และสต็อกผ่าน HTTP/API handlers ของแอปจริง โดยเปิด test server บน loopback พอร์ตสุ่ม การสร้างสูตรเริ่มต้นและควบคุมนาฬิกาเป็น fixture SQL ในฐานข้อมูลจำลอง ไม่ได้ INSERT ออเดอร์หรือประวัติขายเพื่อข้าม business logic

ใช้ Node Date และ PostgreSQL `public.now()` จำลองเวลาเฉพาะ process/database ทดสอบ สร้างฟังก์ชันก่อน migration เพื่อให้ default timestamps ใช้นาฬิกาเดียวกัน ตั้ง `search_path=public,pg_catalog` เฉพาะฐานจำลอง ไม่เปลี่ยนนาฬิกา Windows และไม่เพิ่มช่องทางเปลี่ยนเวลาให้ API จริง ตั้ง `synchronous_commit=off` เฉพาะการเชื่อมต่อจำลองเพื่อเพิ่มความเร็ว; จึงไม่ได้ใช้รอบนี้ทดสอบความทนทานต่อไฟดับ

## ออกแบบข้อมูลและป้องกันข้อมูลอนาคต

ใช้ seed `20261103` และกติกายอดขายที่ประกาศก่อนรัน: ความต้องการแบบ Poisson แตกต่างตามเมนู วันเสาร์อาทิตย์เพิ่ม 35%, แนวโน้มเพิ่มช้า, ความผันผวนรายวัน และเหตุการณ์เพิ่มยอดเป็นครั้งคราว ไม่ใช้คำตอบจากโมเดลสร้างยอดขายหรือปรับสูตรให้โมเดลชนะ

จำลอง 211 วัน สิ้นสุดเมื่อวานตาม Asia/Bangkok:

1. 180 วันแรกเป็นช่วงขายสำหรับเตรียมข้อมูล
2. เช้าวันที่ 181 ออกพยากรณ์ **วันถัดไป 30 วัน** เก็บ archive/export/checksum ให้เสร็จก่อนสร้างยอดช่วงทดสอบ แล้วจำลองยอดของวันออกพยากรณ์ต่อ
3. อีก 30 วันเป็นคำตอบที่กันไว้ ตรวจพยากรณ์ frozen 240 คู่เมนู-วันกับยอดส่งมอบ
4. หลังสิ้นสุด สร้างพยากรณ์ใหม่จากประวัติล่าสุดสำหรับวันพรุ่งนี้ถึงอีก 30 วันไว้ตรวจต่อ

วันที่ออกพยากรณ์ไม่ถูกนำเข้า history เพราะแอปไม่นำวันปัจจุบันที่ยังไม่สมบูรณ์มาใช้ โมเดลรับประวัติสูงสุด 120 วันตามสัญญาปัจจุบัน แม้ฐานจำลองมีประวัติครบ 211 วัน การทดสอบจึงไม่ใช่การเทรนด้วยข้อมูลทั้งหมด 180 วันโดยตรง

ผลหลักใช้โมเดลเลือกอัตโนมัติของแอปตาม validation ภายในชุดฝึก เปรียบเทียบกับ weekly naive ที่ใช้ข้อมูล snapshot เดียวกันและเดินข้ามวันที่ออกพยากรณ์อย่างถูกต้อง ไม่ปรับโมเดลตาม holdout นี้ ไม่เปลี่ยนโมเดลหรือ forecast ร้านจริง

บริการ FastAPI ของรอบจำลองแยกพอร์ต 18002 และ `FORECAST_MODEL_DIR` แยกในโฟลเดอร์รอบนั้น จึงไม่เขียน artifact จำลองทับ runtime ของบริการร้านจริง

`data_mode=actual` และ `history_source=actual` ใน archive หมายถึงรายการที่ส่งมอบผ่าน order ledger ภายใน **ฐานจำลอง** ตาม schema ของแอปเท่านั้น ไฟล์ทุกชุดระบุ `synthetic: true` หรือ `data_origin=synthetic` ห้ามนำรอบนี้ไปรวมกับคะแนนจริงของร้าน

## ผลลัพธ์

- `report.json`: จำนวนสถานการณ์ ผลกระทบยอด คะแนน holdout และวันที่พยากรณ์ถัดไป
- `report.md`: รายงานอ่านง่าย พร้อมคะแนนเทียบ baseline และแยกเมนู (สร้างด้วย `simulation:report`)
- `frozen-holdout-forecast.json`: พยากรณ์ที่เก็บก่อนสร้างคำตอบ พร้อม exact input/checksum
- `future-30-days.json`: พยากรณ์ใหม่ 30 วันหลังจบการจำลอง
- `daily.csv`: ข้อมูลล่าสุด 120 วัน / 960 แถวตามขอบเขต history ของโมเดล
- `daily-full.csv`: ข้อมูลครบ 211 วัน / 1,688 แถว (สร้างด้วย `simulation:report`)
- `evaluation-details.json`: คะแนนแยกเมนู และ cumulative horizons 1/7/14/30 วัน

`simulation:report` อ่านเฉพาะรอบที่สำเร็จและตรวจ marker `synthetic-only` ก่อน export โดยใช้ read-only transaction สำหรับสรุป ledger

`simulation:preview` เปิดแอปปกติบน `http://localhost:3002` เฉพาะ loopback พร้อมบริการโมเดลแยก 18002 บัญชีทดสอบอยู่ในไฟล์ส่วนตัว `review-access.json` ของรอบนั้น ไม่พิมพ์รหัสผ่านใน log และไม่ commit ไฟล์นี้ ชื่อผู้ใช้ในเว็บแสดง **ข้อมูลจำลอง · เจ้าของร้าน** พอร์ต 3001 และ runtime โมเดลร้านจริงไม่ถูกเปลี่ยน ตัว preview เปลี่ยน `public.now()` เฉพาะฐานจำลองให้กลับใช้เวลาจริงสำหรับ session/การใช้งานต่อ ไม่เปลี่ยน timestamps ที่บันทึกแล้ว เมื่อต้องการหยุดกด Ctrl+C

หน้าพยากรณ์ของ preview ใช้สัญญาเดียวกับแอปหลัก ดังนั้นคำว่า “ข้อมูลจริง” ภายในหน้านี้หมายถึง order ledger ของ **ร้านจำลอง** เท่านั้น ห้ามนำคะแนนไปอ้างว่าเป็นความแม่นยำกับลูกค้าจริง

การจำลองระดับ API ไม่แทนการทดสอบ browser interaction, SSE reconnect, accessibility, เครือข่ายมือถือ, เครื่องพิมพ์หรือรับเงินจริง ต้องใช้ browser suite (`npm run test:e2e`) และทดสอบหน้างานแยก ผล holdout เป็นเพียงหนึ่งช่วงของโลกที่เราสร้างขึ้น แม้คะแนนดีขึ้นก็ยังไม่ยืนยันความแม่นยำเมื่อพบยอดขายจริงหรือเหตุการณ์ที่ไม่อยู่ในกติกาจำลอง
