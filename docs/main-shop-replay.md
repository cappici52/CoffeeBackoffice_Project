# จำลองการขายผ่านร้านเดิมในฐานข้อมูลหลัก

คำขอผู้ใช้วันที่ 3 พฤศจิกายน 2026: จำลองการทำงานย้อนหลังหลายเดือนเหมือนการทดลองเดิม แต่ **ใช้ฐานข้อมูลหลักและเมนู/ราคา/ตัวเลือก/สูตร/วัตถุดิบที่มีอยู่จริงในแอป** ไม่สร้างร้านตัวอย่างอีกชุด และไม่ย้ายยอดจากฐานจำลอง 211 วันเดิม

## การทำงาน

```powershell
npm run simulation:shop
```

คำสั่งนี้มีผลเขียนฐานข้อมูลหลัก ใช้เฉพาะเครื่องพัฒนา PostgreSQL loopback และต้องมี `--main-shop` ในคำสั่ง Node (npm script ใส่ให้แล้ว) ไม่ใช่คำสั่งติดตั้ง/เริ่มแอปตามปกติ และไม่รันใน CI อัตโนมัติ

ก่อนรันให้หยุด API/worker ของร้านชั่วคราวเพื่อไม่ให้มีรายการใช้งานพร้อมกัน ต้องมีบัญชี owner/manager ปัจจุบันใน `.env` ตามค่า bootstrap, ตาราง QR เปิดใช้งาน และเมนูที่ไม่ archive ทุกเมนูพร้อมขายพร้อมสูตร สคริปต์ไม่เปลี่ยนรหัสผ่านหรือสร้างพนักงานใหม่

เครื่องมือสำรองฐานด้วย `pg_dump` และตรวจ checksum ก่อน migration/การเพิ่มรายการ เก็บ backup และข้อมูลกำกับใน `.local/shop-replay/<run-id>/` ซึ่งไม่ commit ใช้ advisory lock กันสองรอบทำงานพร้อมกัน และปฏิเสธการรันซ้ำหรือช่วงวันที่ทับ order/day closing เดิม

ใช้ seed `20261103` จำลองขาย 211 วัน สิ้นสุดสองวันก่อนวันที่รัน เพื่อหลบรายการเดิมของเมื่อวาน สร้าง pattern จาก Poisson/วันหยุด/แนวโน้ม/เหตุการณ์ที่ประกาศใน simulation-plan ไม่อ้างว่าเรียนรู้ pattern จริงจากประวัติเดิมที่ยังมีเพียงหนึ่งวัน ใช้ราคาปัจจุบันและสูตรปัจจุบันตลอดช่วงจำลอง ไม่อ้างว่าเป็นราคาหรือสูตรที่ร้านเคยใช้ในอดีต

owner ของร้านเรียก HTTP handlers จริงผ่าน `createApp` กับฐานหลัก ตั้งแต่ QR/POS สั่ง → ยืนยัน/ตัดสูตร → KDS เตรียม/พร้อม → ส่งมอบ → รับชำระภายหลัง → ปิดวัน มีตัวเลือกจริงตามเมนู การยกเลิกก่อน/หลังเตรียม คืนเงิน เติมวัตถุดิบที่ขาดผ่าน stock API ตรวจคำสั่งซ้ำและยอดเงินสด+PromptPay

ไม่ INSERT order/items/payment/stock เพื่อข้าม business logic มีเพียง adapter ของตัวรันที่แทน clock และเพิ่ม provenance ให้คำสั่ง SQL ของ process นี้: order.created_at/payment.paid_at/status timestamps เป็นเวลาเหตุการณ์จำลอง ส่วน stock movement/audit ingestion timestamps ยังเป็นเวลาที่รันจริง ทำให้บัญชี stock balance เดิมเดินต่อได้ถูกต้อง ไม่เปลี่ยน default/function/นาฬิกาของฐานข้อมูลหรือของ API ปกติ และไม่แก้เวลารายการเดิม

Session ของ **instance ที่รัน replay เท่านั้น** มีอายุ 168 ชั่วโมงจำลองและล็อกอินใหม่ทุก 6 วัน การหมดอายุ session ของแอปปกติยังใช้ config เดิม การเขียน replay ใช้ asynchronous commit เฉพาะ connection ของตัวรัน; root connection ที่ประกาศจบงานใช้ synchronous commit ตามปกติ

ตัวรันปฏิเสธเริ่มหากพอร์ต API ปกติยังเปิดอยู่ Nightly worker พักการออกพยากรณ์ระหว่างมีรอบ running หรือ failed ที่ยังไม่ย้อนกลับ เพื่อไม่ออกผลจากประวัติที่กำลังสะสม เมื่อรอบ complete หรือ failed ที่ rolled_back แล้วจึงกลับทำงานตามปกติ

## ระบุแหล่งที่มา

Migration 011 เพิ่มตารางรอบ/เมนูที่เข้าร่วม และ `simulation_run_id` บน orders/payments/stock_movements/day_closings/forecast_runs รายการสั่งและเหตุผล stock มี `[SIMULATION <run-id>]` ด้วย เมนู/ราคา/ตัวเลือก/สูตร/โต๊ะเดิมไม่ถูกแก้

วันที่ปิดร้านในรอบจำลองเป็นหลักฐาน zero observation ของเมนูที่เข้าร่วม แม้จำลองเวลาก่อนวันสร้างเมนูจริง ไม่ย้อนไปแก้ `forecast_since` หรือวันสร้างเมนูดั้งเดิม

ทุกหน้าหลังเข้าสู่ระบบแจ้งว่าฐานนี้มีรายการจำลอง และรายงาน/stock รวมรายการเหล่านี้ `data_mode=actual` หมายถึงอ่าน order ledger ของร้าน ไม่ได้หมายความว่าทุกรายการเป็นลูกค้าจริง `forecast_runs.contains_simulated_sales` ระบุ lineage ของชุดฝึก รวม zero observations จากวันปิดจำลอง

คะแนนจาก run ที่มี lineage นี้แยกกลุ่ม `simulation` ไม่รวมกับ genuine-sales MAE/WAPE แม้ทุก snapshot row มี source `actual` ห้ามนำคะแนนจำลองไปอ้างว่าเป็นความแม่นยำกับลูกค้าจริง

## การพยากรณ์และตรวจสอบ

หลังจำลอง 180 วัน ออกพยากรณ์วันถัดไป 30 วัน เก็บ immutable snapshot และ SHA-256 ก่อนสร้างคำตอบช่วงนั้น วันออกพยากรณ์ไม่นำเข้า history ตามสัญญาวันปัจจุบันของแอป โมเดลใช้สูงสุด 120 วัน ไม่เติม unknown เป็นศูนย์นอกวันปิดที่ยืนยันแล้ว

จบ 211 วัน เปรียบเทียบ 30 วันท้ายกับ weekly naive จาก snapshot เดียวกัน ตรวจคะแนนจาก API ต้องตรงกับการคำนวณอิสระ แล้วสร้างรอบพยากรณ์อีก 30 วันจากข้อมูลล่าสุดไว้แสดงในแอปหลัก

ตรวจ hash ของ orders/payments/movements/closings/forecast runs ที่ไม่มี simulation ID และเมนู/ตัวเลือก/สูตร/โต๊ะเดิมก่อน–หลังให้ตรงกัน ตรวจบิลค้างของรอบจำลองเป็นศูนย์ ยอดรับชำระตรงบิล จำนวนวันปิดครบ และ stock balance ตรงผลรวม journal ทั้งร้าน ผลและ snapshot อยู่ใน `report.json`, `frozen-holdout.json`, `future-30-days.json` ใต้โฟลเดอร์รอบ

หากหยุดกลางทาง รอบมีสถานะ failed และไม่เริ่มซ้ำทับข้อมูลที่มีอยู่ ต้องตรวจ/กู้คืนเฉพาะรอบนั้นก่อน รักษา backup ไว้เสมอ ห้ามลบ archive ที่ป้องกัน UPDATE/DELETE หรือ restore ทับฐานหลักอัตโนมัติ

หลังจบเปิดแอปตามปกติด้วย `npm run local:lan` ใช้บัญชีร้านเดิมบนพอร์ต 3001 ข้อมูลและกราฟอยู่ในฐานหลัก ไม่มีเว็บร้านใหม่บนพอร์ต 3002 หรือการคัดลอกรายการจากฐานทดลองเก่า
