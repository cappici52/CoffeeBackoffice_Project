# แผนประเมินพยากรณ์ด้วยข้อมูลร้าน

## สิ่งที่พิสูจน์แล้วและสิ่งที่ยังพิสูจน์ไม่ได้

โมเดล ProjectA เชื่อมผ่าน native JSON และตรวจผลเทียบต้นฉบับแล้ว ระบบเทรน candidate จากประวัติร้านและเลือกเทียบ weekly baseline ได้ แต่ข้อมูล demo ของร้านไม่พิสูจน์ความแม่นยำในการใช้งานจริง

ผลทดลองข้อมูล Coffee Sales ภายนอกมี protocol/holdout/artifacts ใน [coffee-sales-evaluation.md](coffee-sales-evaluation.md) candidate ที่ frozen holdout มี WAPE ประมาณ 63.97% เทียบ baseline rolling mean ประมาณ 61.16% จึง **ไม่ได้ promote** โมเดลนั้นไปแอป ข้อมูลจาก vending machine และจำนวนธุรกรรมไม่เท่ากับยอดขายร้านนี้โดยตรง ห้ามรายงานว่าโมเดลแม่นยำกว่าวิธีพื้นฐานจากผลดังกล่าว

## เป้าหมายและหน่วยข้อมูล

เป้าหมายปัจจุบันคือจำนวนหน่วยขายต่อเมนูต่อวันปฏิทิน Bangkok ไม่ใช่ปริมาณวัตถุดิบโดยตรง ปริมาณเตรียมคูณสูตรพื้นฐาน ไม่รวมพฤติกรรมเปลี่ยนตัวเลือกทั้งหมด `sales_daily.source=actual` มาจากรายการชำระตามวันรับเงิน ดังนั้นกรณีเสิร์ฟข้ามวันแต่ชำระอีกวันต้องระบุว่าเป็น paid-sales proxy ของ demand

เก็บ menu ID คงที่ วัน จำนวนขาย ราคา และเวลาที่สร้าง forecast ไม่แก้ actual ย้อนหลังให้ผลดีขึ้น บันทึกเหตุการณ์นอกระบบ เช่น ปิดร้าน stockout เมนูใหม่ โปรโมชั่น และวันหยุด แยกไว้เพื่ออธิบายข้อจำกัด วันไม่มีข้อมูลไม่เท่ากับศูนย์ ปิดวันผ่านระบบเพื่อให้ยืนยัน zero-sales ของเมนูที่มีอยู่แล้วได้ ไม่เติมศูนย์ก่อนวันที่เมนูเริ่มมีอยู่

## ขั้นตอนที่ทำซ้ำได้

1. ใช้ระบบรับรายการและปิดวันอย่างต่อเนื่อง ตรวจยอดเงินจริงทุกวัน เก็บ actual อย่างน้อย 28 วันต่อเนื่องสำหรับ weekly; 84 วันสำหรับเริ่มเลือกโมเดลร้าน ประวัติมากกว่านี้ช่วยให้เหลือช่วงประเมินอิสระ
2. กำหนดช่วง train/validation/test ด้วยวันที่ก่อนทดลอง แบ่งตามเวลา ห้ามสุ่มแถวข้ามวัน ตัวอย่างเมื่อมี 140 วัน: 84 วันแรก train, 28 วันถัดไปเลือกวิธี/ค่า, 28 วันสุดท้ายทดสอบครั้งเดียว ปรับช่วงตามปริมาณข้อมูลจริงพร้อมแจ้งเหตุผลก่อนดูผล
3. การเลือกในแอปใช้ validation 28 วันที่อยู่ก่อน forecast origin เปรียบเทียบ weekly naive, ProjectA และ shop XGBoost ด้วย MAE ต่อเมนู ข้อมูลราคาใน validation ไม่ถูกใช้แทนราคาที่รู้ ณ origin
4. เก็บ forecast ล่วงหน้าก่อนวันเป้าหมาย แล้ววัดกับ actual ภายหลัง การแก้/สร้าง forecast ของวันอนาคตซ้ำต้องกำหนดรอบที่จะใช้ประเมินชัดเจนก่อนวัด แอปเก็บผลล่าสุดต่อเมนู/วัน จึงควร export snapshot ของรอบที่กำหนดเป็นไฟล์วิจัยส่วนตัวก่อนอัปเดตรอบถัดไป
5. รายงานทั้ง aggregate และรายเมนู แยก horizons 1/7/14/28 วันตามที่ตั้งใจประเมิน ระบุ sample count, วัน/เมนูที่ตัดออก และช่วงที่ไม่ครบ อย่าเทียบคะแนนที่คำนวณคนละช่วงข้อมูล

## ตัวชี้วัด

ให้ `y` เป็นยอดจริง, `p` เป็นพยากรณ์ และ `n` เป็นจำนวนคู่ที่มีข้อมูล:

- MAE = `sum(abs(y-p)) / n` หน่วยขายต่อเมนู/วัน
- RMSE = `sqrt(sum((y-p)^2) / n)` เน้นความผิดพลาดขนาดใหญ่
- WAPE = `100 * sum(abs(y-p)) / sum(y)` ถ้า sum(y)=0 ให้รายงานว่าไม่กำหนด
- MAPE = ค่าเฉลี่ย `100*abs(y-p)/y` เฉพาะคู่ที่ y>0 พร้อมจำนวนคู่ที่ตัดออก
- Bias = `sum(p-y) / n` ช่วยเห็นการเตรียมมาก/น้อยเกินไป

หน้าแอปปัจจุบันแสดง MAPE/RMSE จาก actual คู่กับ forecast ที่สร้างก่อนวันเป้าหมาย ไม่รวม demo และ backcast ค่าที่เหลือใช้รายงานการทดลองแยก ไม่ถือว่ามีอยู่บนหน้าเว็บแล้ว ไม่มีช่วงความเชื่อมั่นที่สอบเทียบไว้ จึงไม่สร้างตัวเลขช่วงขึ้นมา

## เกณฑ์ตัดสินก่อนเปิดผลทดสอบ

เขียน baseline และข้อกำหนดร้านไว้ก่อน เช่น candidate ต้องลด MAE/WAPE เทียบ baseline บนช่วงเดียวกัน และไม่เพิ่มการประเมินต่ำอย่างมากในเมนูหลัก ตรวจผลหลาย origins เมื่อข้อมูลพอ หากแพ้ให้คง baseline และรายงานผลจริง ไม่เลือกเฉพาะเมนู/ช่วงที่ชนะ ไม่ปรับ hyperparameter หลังเห็น test แล้วเรียกคะแนนเดิมว่า independent test

ผลระบบเลือกวิธีจาก validation ไม่ใช่ independent test accuracy การใช้ข้อมูลร้านจริงเพิ่มอาจไม่ทำให้ XGBoost ชนะเสมอ ความถูกต้องของข้อมูลและประโยชน์ต่อการเตรียมของสำคัญกว่าชื่อโมเดล
