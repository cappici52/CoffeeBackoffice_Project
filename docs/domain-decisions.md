# Initial domain decisions

These are implementation choices for the authorized core build, complementing the supplied specification. They are not instructions embedded in the supplied document or claims about external payment settlement.

- Monetary values are integer satang. The server calculates all prices from current catalog data and selected options; clients cannot submit prices. Order items snapshot names, prices, costs, recipe ingredients, steps and target times so later menu changes do not rewrite historical orders.
- Creating and paying an order can be one transaction. A UUID request key plus a payload hash prevents retries or simultaneous submissions from creating duplicate orders. A changed payload using an existing key is rejected.
- Payment is recorded after staff verifies cash or incoming PromptPay funds. There is no slip verification or payment-gateway call. Staff confirmation of dine-in orders deducts recipe ingredients exactly once and admits the order to KDS without payment. Advance POS payment also confirms an order. Later payment never deducts the ingredients again. All ingredient locks are acquired in a stable order.
- Options can add ingredients or replace an existing recipe ingredient. Replacing with quantity zero removes the ingredient (for example no syrup). Two options cannot both replace the same ingredient. Cost snapshots follow the selected recipe.
- Staff progress confirmed order items from pending to preparing to ready, with timestamps. Whole-order status reflects all items. Cashiers complete ready orders after handoff. Kitchen can access KDS and its own account, never sales/cost data or user lists.
- Cancelling unpaid pending orders is allowed for cashier/manager/owner. Refunding paid active orders requires owner/manager, a reason and explicit confirmation that money was actually returned manually. Ingredients return to stock only if no item has started. Started ingredients remain consumed; cancellation does not invent reusable stock. Served orders may still be unpaid; staff records payment after dining without changing fulfillment status. Completed fulfillment cannot be cancelled; partial refunds and post-closing corrections are outside the core specification.
- Reports recognize net paid orders on their payment date in Asia/Bangkok, excluding refunded orders. Refund totals are shown separately. Gross recipe margin is owner-only and excludes overhead and waste, so it is not accounting net profit. Historical demo sales never become payments or actual report revenue.
- Day close checks there are no pending/preparing/ready orders or served-but-unpaid orders created on or before the selected day. It stores a summary and prevents further payment/refund changes for that business day. Payment, cancellation and closing share a transaction lock. Dates and audit timestamps are retained, not silently changed.
- Products are archived and ingredients are deactivated, preserving order/movement references. Ingredients must have zero stock and no recipe/option reference before removal. Only unreferenced categories can be deleted. User accounts are deactivated rather than hard-deleted. No automatic personal-data retention/deletion policy is implied.
- Managers manage cashier/kitchen users only. Owners can create privileged accounts. A user cannot remove their own access; at least one active owner remains. Password/role/deactivation changes revoke applicable sessions immediately.
- Forecasts are supplied by a separate FastAPI adapter, validated before atomic persistence and versioned. The imported ProjectA XGBoost, newly trained shop-history XGBoost and weekly baseline are selected through prior-only recursive validation. New forecasts have no invented interval; legacy mock intervals stay explicitly labeled. See forecast-integration.md for the exact history and model-selection contract. Ingredient recommendations use base recipes and current stock, excluding future option choices. Metrics show no value until comparable historical predictions exist.
- The forecast worker runs after 02:00 Asia/Bangkok, catches up if started later, records one successful run per day and retries failures each minute. It needs to stay running. Forecast generation now trains a local candidate when history meets the documented minimum; each prediction retains the method/version and actual/demo provenance.

Forecast redesign update: new rounds follow [forecast-v4.md](forecast-v4.md), which supersedes the earlier recursive/ProjectA selection and unavailable-interval decisions. Sales/payment/stock rules are unchanged. The conservative mean28 policy is explicit; auto model selection is an alternative. Cohorts and empirical range coverage are recorded and evaluated separately.
