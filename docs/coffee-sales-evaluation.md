# ทดลองเทรนด้วยข้อมูล Coffee Sales จริง

วันที่ตรวจ: 2 พฤศจิกายน 2569 (Asia/Bangkok)

**ผลตัดสิน: เทรนและประเมินเสร็จแล้ว แต่ยังไม่เปิดใช้โมเดลนี้แทนวิธีพยากรณ์ในแอป** เพราะแพ้วิธีเฉลี่ยย้อนหลัง 28 วันทั้งช่วง validation และช่วง holdout จึงไม่ควรบังคับใช้ XGBoost เพียงเพราะเทรนจากข้อมูลจริง

## แหล่งข้อมูลและสิทธิ์

- ต้นทาง: [Coffee Sales — Yaroslav Isaienkov / ihelon](https://www.kaggle.com/datasets/ihelon/coffee-sales) ผู้เผยแพร่ระบุว่าเป็นรายการขายจากตู้ขายกาแฟ
- ตรวจข้อมูลต้นทางผ่าน [Kaggle public metadata](https://www.kaggle.com/api/v1/datasets/list?search=coffee%20sales&user=ihelon) พบสิทธิ์ **CC0: Public Domain** และวันที่แก้ไขชุดข้อมูล 25 มีนาคม 2025 ไม่ได้อาศัยสิทธิ์จากสำเนาบุคคลที่สามเพียงอย่างเดียว
- ใช้ `index_1.csv` เท่านั้น: **3,636 รายการ, 8 ชนิดเครื่องดื่ม, 1 มีนาคม 2024–23 มีนาคม 2025, 381 วันที่มีรายการขาย** ไม่พบแถวซ้ำตรงกันทุกคอลัมน์
- ไม่รวม `index_2.csv` เพราะช่วงเวลา โครงสร้างคอลัมน์และชุดเมนูต่างกัน และไม่มีหลักฐานเพียงพอว่าเป็นเครื่อง/ช่องทางเดียวกัน
- ชุดข้อมูลไม่มีคอลัมน์จำนวนแก้ว เป้าหมายจึงเป็น **จำนวนรายการขายเครื่องดื่มต่อเมนูต่อวัน** ไม่อ้างว่าตรวจยืนยันจำนวนแก้วจาก POS แล้ว
- วันทั้งเครื่องที่ไม่มีข้อมูล 7 วันถือว่า **ไม่ทราบข้อมูล** ไม่เติมยอดศูนย์ ส่วนเมนูที่เคยปรากฏแล้วแต่ไม่มีรายการในวันที่เครื่องมีรายการอื่น นับเป็นศูนย์รายการขายโดยมีสมมติฐานว่าเมนูยังมีให้เลือก ข้อมูลไม่มีสถานะของหมดหรือเวลาเปิดเครื่อง จึงไม่ใช่การวัดอุปสงค์ที่ปราศจากข้อจำกัดสต็อก
- เก็บวันตามปฏิทินต้นฉบับ ไม่เปลี่ยนปีให้เหมือนยอดปัจจุบันของร้าน ไม่เดาสกุลเงินหรืออัตราแลกเปลี่ยน

ข้อมูลดิบและ ZIP อยู่ใน `.local/datasets/coffee-sales/` ซึ่ง Git ไม่ติดตาม ส่วนข้อมูลที่นำเข้า Git เป็นข้อมูลรวมรายวัน `date,product,transactions` เท่านั้น ไม่มีรหัสบัตร วิธีชำระเงิน หรือตัวระบุลูกค้า และไม่ได้นำเข้าตารางยอดขาย/ออเดอร์/การชำระ/สต็อกของร้าน

## วิธีเทรนและการกันข้อมูล

ทดลอง XGBoost สอง objective ที่กำหนดไว้ก่อนประเมิน: Poisson และ absolute error โดยใช้ lag 1/7/14/28 วัน, ค่าเฉลี่ย 7 วัน, วันในสัปดาห์ และเดือน จำนวนย้อนหลังและเป้าหมายหารด้วยค่าเฉลี่ย **28 วันก่อนหน้าเท่านั้น** เพื่อช่วยถ่ายโอนรูปแบบจากเครื่องที่ยอดน้อยไปยังร้านที่ยอดต่างกัน โดยไม่ใช้ราคาต่างสกุลเงิน ชื่อเมนู รหัสสินค้า หรือตัวระบุลูกค้าเป็น feature

พารามิเตอร์คงที่: 220 boosting rounds, depth 3, learning rate 0.05, subsample 0.85, colsample 0.8, min child weight 5, lambda 5, seed 42, CPU 2 threads ไม่มีการค้นพารามิเตอร์บน holdout

แต่ละตัวอย่างเทรนต้องมีข้อมูลย้อนหลังครบ 28 วันตามปฏิทิน หน้าต่างที่ผ่านวันไม่ทราบข้อมูลจะถูกเว้น ไม่เติมศูนย์ให้โมเดล

- **Validation:** เทรนด้วยข้อมูลถึง 29 ตุลาคม 2024 แล้วพยากรณ์แบบ recursive ช่วง 30 ตุลาคม–26 พฤศจิกายน 2024 เป็นหน้าต่างครบ 56 วันล่าสุดที่มีทั้งประวัติ 28 วันและเป้าหมาย 28 วัน ก่อนช่วงทดสอบสุดท้าย การเลือกหน้าต่างพิจารณาความครบของวันที่ ไม่พิจารณาคะแนนโมเดล
- เลือก XGBoost แบบ absolute error และ baseline ค่าเฉลี่ย 28 วันจาก validation โดยเปรียบเทียบ MAE
- **Holdout:** นำวิธีที่เลือกแล้วมาเทรนด้วยข้อมูลถึง 23 กุมภาพันธ์ 2025 และพยากรณ์ 24 กุมภาพันธ์–23 มีนาคม 2025 เป็นเวลา 28 วัน รวม **224 คู่เมนู–วัน** ไม่ใช้ยอดจริงระหว่างทางป้อนกลับในการพยากรณ์
- ไม่เปลี่ยน feature พารามิเตอร์ หรือผู้ชนะหลังดูผล holdout การรันตรวจซ้ำเป็นการทดสอบความทำซ้ำได้ของขั้นตอนเดิม ไม่ใช่ holdout อิสระใหม่
- ไฟล์โมเดลที่เก็บไว้เป็นการ refit ด้วยข้อมูลที่ทราบครบถึง 23 มีนาคม 2025 หลังประเมินจบแล้ว คะแนน holdout เป็นคะแนนของกระบวนการที่เทรนก่อนช่วงทดสอบ ไม่ใช่คะแนน in-sample ของไฟล์ refit นี้
- เก็บ `holdout-model.json` ซึ่งเทรนก่อนช่วง holdout แยกจาก `model.json` ที่ refit แล้ว เพื่อคำนวณคะแนนในรายงานซ้ำจาก estimator ตัวเดียวกันโดยตรง การเทรนใหม่บนต่าง OS/build ไม่รับประกันค่าน้ำหนักเหมือนกันทุกหลัก: รอบ CI Linux ให้ WAPE 61.97% ขณะที่ estimator จาก Windows ที่บันทึกไว้ได้ 63.97% ทั้งสองยังแพ้ค่าเฉลี่ย 61.16% ไม่ได้ปรับพารามิเตอร์เพื่อเปลี่ยนผล holdout ดู [ข้อสังเกตการทำซ้ำของ XGBoost](https://xgboost.readthedocs.io/en/release_3.0.0/faq.html#slightly-different-result-between-runs) และ environment ที่บันทึกใน manifest

## ผลช่วง holdout

WAPE ต่ำกว่าดีกว่า และเป็น **ความคลาดเคลื่อน ไม่ใช่เปอร์เซ็นต์ความแม่นยำ**

| วิธี | MAE (รายการ/เมนู/วัน) | RMSE | WAPE | จำนวนพยากรณ์รวม |
|---|---:|---:|---:|---:|
| ยอดสัปดาห์ก่อน | 1.2455 | 1.7991 | 68.55% | 444.00 |
| ค่าเฉลี่ยย้อนหลัง 28 วันแบบ recursive | **1.1112** | **1.5127** | **61.16%** | 400.53 |
| XGBoost relative absolute error | 1.1624 | 1.7922 | 63.97% | 214.42 |

ยอดจริงรวมช่วงทดสอบคือ **407 รายการ** โมเดล XGBoost มีแนวโน้มพยากรณ์ต่ำ โดยเฉพาะข้อมูลขายที่ไม่สม่ำเสมอ แม้จะดีกว่าวิธียอดสัปดาห์ก่อนใน WAPE ก็ยังแพ้ baseline อีกตัวที่เลือกไว้ก่อนดู holdout และค่าเฉลี่ยของ baseline ยังมีความคลาดเคลื่อนสูง จึงไม่อ้างว่าชุดข้อมูลนี้ทำให้พยากรณ์ร้านเราได้แม่นยำ

รายละเอียดคะแนนรายเมนูอยู่ใน [evaluation.json](../forecast-service/evaluations/coffee-sales/evaluation.json) โดย model manifest ระบุ `deployment_approved=false` ไฟล์ทั้งหมดอยู่ในโฟลเดอร์ `evaluations` แยกจาก `artifacts` ที่แอปโหลด ไม่มีการเพิ่ม candidate นี้เข้าสู่ตัวเลือกของบริการจริงหรือเปลี่ยนผลพยากรณ์ที่บันทึกอยู่ในร้าน

## ทำซ้ำ

จากรากโปรเจกต์ หลังติดตั้ง `forecast-service/requirements.txt`:

```powershell
# ดาวน์โหลดต้นฉบับ ตรวจสิทธิ์ และเทรนใหม่ (เก็บข้อมูลดิบในโฟลเดอร์ที่ Git ไม่ติดตาม)
.\.venv\Scripts\python.exe forecast-service/train_external.py --download

# ทำซ้ำแบบ offline จากข้อมูลรายวันที่ตัดตัวระบุลูกค้าออกแล้ว
.\.venv\Scripts\python.exe forecast-service/train_external.py --prepared forecast-service/evaluations/coffee-sales/daily.csv --output .local/coffee-sales-replay

# ทดสอบทั้งระบบโมเดลเดิมและ pipeline ข้อมูลจริง
.\.venv\Scripts\python.exe -m unittest discover -s forecast-service
```

ไฟล์ `provenance.json` เก็บ URL ต้นทาง สิทธิ์ วันที่แก้ไข ข้อจำกัด และ SHA-256 ของ ZIP, CSV ต้นฉบับ และ CSV รายวัน ส่วน `manifest.json` เก็บเวอร์ชัน/feature/checksum ทั้งโมเดลก่อน holdout และโมเดล refit พร้อม OS/Python/NumPy/XGBoost ที่ใช้เทรน การแก้ไฟล์ข้อมูลหรือโมเดลโดยไม่ปรับหลักฐานจะทำให้การตรวจ checksum ไม่ผ่าน การตรวจ CI แยกการคำนวณคะแนนด้วยโมเดลที่บันทึกไว้จากการรันเทรนใหม่ และยังตรวจว่าผลเทรนใหม่ไม่ผ่านเกณฑ์เลื่อนขึ้นใช้งาน

การทดลองนี้ยืนยันว่าทำ pipeline ด้วยข้อมูลจริงได้ และวัดได้ว่าโมเดลที่ทดลองยังไม่เหมาะกับการเลื่อนขึ้นใช้งาน การพัฒนารอบถัดไปควรมีข้อมูลร้านกาแฟที่จำนวนขายต่อเมนูชัดเจน สถานะเปิดร้าน/เมนู และช่วงทดสอบใหม่ที่ยังไม่เคยใช้ประเมิน หากต้องการยืนยันความแม่นยำกับร้านเรา ยังต้องวัดกับยอดจริงของร้านเราเอง
